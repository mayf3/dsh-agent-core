# First-target implementation interface for the single Owner operation

This is an implementation/packet interface under accepted Spec 3986553 and independently reviewed design f88fb71. It does not authorize operation, attest lifecycle retirement, claim production acceptance, or replace the parent's exact materializer/runbook review. All source work and tests here are nonproduction.

## Frozen constructors and wire records

`model::AdoptionGrant`, `AdoptionRelease`, `StandingActivationGrant`, `FirstLiveMaterializationReceipt` are the authoritative Rust serialization definitions in `src/model/adoption.rs`. Grants use existing `Signed<T>` and domain-separated Authority signatures: `FirstTargetAdoption` and `FirstTargetStandingActivation`. No ordinary issuer endpoint signs either type.

AdoptionRelease contains exactly `goal_id`, `acceptance_revision`, `source_sha`, `artifact_sha256`, `manifest_digest`. The package can freeze these immutable public source/artifact coordinates before a live review job/lease exists. The actual complete authenticated Proposal is durably pinned once in `adoption_proposals` before canonical unit creation. A changed request ID, policy-bearing Proposal or signed record cannot replace this pin. This realizes the reviewed prepare→observe sequence without a time-dependent Proposal-digest circular dependency.

AdoptionGrant additionally binds version 1; unique operation ID; exact package and controller binary hashes; host/profile/profile hash; native enrollment; configuration; issuer bindings; attributable Owner acceptance and authenticated lifecycle evidence hashes; actual complete initial face and service generation; raw initial canary plan SHA; signed observer policy digest; issued/expires Unix seconds (maximum one day). These are mandatory bindings, not inferred PASS fields.

Configuration adds only default-omitted `first_target_adoption: Option<String>`. Its value is the exact **operation ID**, not grant digest, avoiding configuration→grant→configuration recursion. With this field present, ordinary daemon/Train/issuer startup is blocked even before a Queue reservation exists, and stays blocked until that immutable operation's separate standing activation receipt is durable. Baseline publication alone never enables admission. Legacy configuration bytes omit this field unchanged.

NativeEnrollment adds only default-omitted `runtime_startup`. Absent/`legacy` retains exact prior serialization/argv. `catchup-zero` means exactly the already observed fixed Runtime argv suffix `--catchup 0`; it cannot carry arbitrary arguments. Process identity, enrolled plist and stop/census use the same mapping. W1/W2 are unchanged. The actual parent-observed Runtime uses this suffix; removing it would change existing job behavior.

The signed observer policy payload is:

```json
{"version":1,"profile_id":"<exact enrolled profile>","enrollment_digest":"<canonical native enrollment digest>","runtime_uid":505,"runtime_gid":601,"incident_gid":20,"health_max_age_ms":"<accepted explicit integer>","heartbeat_max_age_ms":"<accepted explicit integer>"}
```

This is a schema illustration, not a production record. The packet constructor must use authenticated actual identities and accepted age bounds; source does not invent defaults. Role is Authority; signing domain is `WatchdogObservationPolicy`. Runtime UID/GID must equal native service enrollment; incident GID must differ from runtime primary GID. Both age bounds are positive, bounded to a day; the packet must satisfy both W1 and W2 accepted heartbeat requirements (one shared maximum must not weaken either).

Verifier ID is exactly `watchdog-current-observation-v1`; Configuration binding remains `{"kind":"external-observation","deadline_ms":<existing accepted bound>}`. Profile `goal_verifiers` maps that exact ID to `local-verifier`. Mapping this ID to installed-byte-only verification is rejected. Existing root `issuer-keys/local-verifier.json` custody, catalog public key and profile role/scope are independently checked; no arbitrary signing surface is added.

`issuer-bindings.json` retains the existing `Vec<bootstrap::IssuerRequirement>` record shape and existing canonical digest convention. This lane adds no alternate binding schema or key material. The materializer must resolve the existing six identities/public keys and preserve independent reviewer custody.

## Paths and operation order

All one-shot commands run in the fixed reviewed `agent-deployd` binary and accept digests only. No command starts/enables a daemon, dispatches a canary, invokes candidate JS, changes sudoers, or installs an application slot.

1. Parent's separately reviewed exact package materializer performs only its Owner-authorized preparation/adoption effects, verifies actual lifecycle denials/retirement and protected native closure, enrolls the two exact continuations without replacing old rows, prepares source policy/config/observer policy and fixed active binding. It must set `first_target_adoption` before active configuration can be used.
2. `Executor::initial_native_observation(&guard)` supplies native enrollment digest, complete face digest, and actual running parent service generation for the exact grant constructor. It verifies initial enrolled hashes/metadata, loader/plist/service dependencies and physical readback under the borrowed permanent guard. This observation does **not** prove Watchdog semantics or business acceptance.
3. Materializer writes Authority-signed grant to `adoption-authorizations/<canonical signed-grant-digest>.json`, signed policy to `watchdog-observer-policy.json`, and root-owned mode-0400 `first-live-materialization.json`. Its exact fields are the `FirstLiveMaterializationReceipt` type. This receipt must come from verified Owner package/lifecycle operations; the consumer merely validates its bindings, it does not create those facts. The one-shot consumer also hashes its current root-owned executable and compares grant/controller hash.
4. `agent-deployd --prepare-adoption <grant-digest>` reserves the exact pending operation, then uses the existing independent review/issuer pipeline for that grant's sole Goal/source. Ordinary preparation remains fenced. This returns the signed Proposal digest; it neither invents Build/Review PASS nor calls Queue mutation.
5. `agent-deployd --adopt-existing <grant-digest> <proposal-digest>` imports the genuine reviewed artifact, verifies complete current release and running native service, creates one honest `ObservedExistingInstallation` baseline at attempt zero, publishes/finalizes it durably. Install/restart counters are zero. A separate standing fence remains.
6. `agent-deployd --begin-watchdog-observation <grant-digest>` authenticates the exact PLANNED `adoptions/<grant-digest>/watchdog/canary-plan.json` raw SHA, requires no already-present canary Job for that logical key, captures current generation/complete face and protected before evidence. The original before record is immutable. Then the separate authorized owning canary operation performs its one genuine no-effect canary; the observer does not execute it.
7. `agent-deployd --finish-watchdog-observation <grant-digest>` reads immutable `canary-created.json`, verifies its raw SHA binding to `canary-creator-readback.json` and the latter to `canary-created-store.json`, and requires the unique stored job to match the exact fixed creator definition. The original plan remains PLANNED and unchanged. It then reads actual authenticated canonical health, durable state and native history/events, correlates the exact plan/job/occurrence and current physical identity, and retains raw evidence. The separately authorized operator must remove only the proven successful canary definition through its existing CAS control before finish, preserving occurrence/history; otherwise the existing semantic isolation gate fails. Unknown is durably retained and fences the lane; it cannot later become a new capture attempt or be overwritten. This command alone does not claim semantic PASS.
8. `agent-deployd --verify-adopted-baseline <grant-digest>` runs the fixed semantic evaluator and normal signed GoalReceipt/CAS/outbox path. Missing evidence is Waiting; no inherited same-source ACCEPTED summary may stand in for current capture. Scoped deployment-child closure is allowed while ordinary mutation remains fenced.
9. Parent's conditional constructor calls `service::adoption::activation_inputs(intake,queue,executor,&guard,&grant)` to receive genuine current baseline/Goal/canary coordinates after fresh physical and native semantic readback. It does not read raw SQL or accept an Agent assertion. It may custody-sign one exact StandingActivationGrant only under its already accepted conditional Owner operation. The grant binds this adoption, honest baseline receipt, canary plan, attributable separate activation Owner acceptance and bounded lease. It is stored in the same digest-only authorization directory.
10. `agent-deployd --complete-adoption-activation <adoption-grant-digest> <activation-grant-digest>` independently rechecks current baseline, signed Goal PASS, fresh native canary proof and Owner grant, and commits one standing activation receipt. It still does not start a service. Actual service enablement/legacy-entry changes belong only to the separately Owner-authorized package.

The scoped raw plan has exactly `status`, `sourceSha`, `canaryAgentId`, `logicalKey`, `at` (canonical UTC ISO), `notAfter` (integer epoch milliseconds, at+180000), and `canaryJobId:null`. The creator readback must occur in [at−240s, at−30s]; the canary result must finish in [at, notAfter]. The parent freezes a sufficiently future absolute at before the bounded independent review; no late plan/digest rewrite is accepted. There is no write to the historical CONTROL plan, before evidence or ACCEPTED receipt.

At every step mismatches stop with retained evidence; request/operation/attempt IDs are not changed to evade uncertainty. Absence of active production bindings is not an empty production database. The normal issuer, daemon and one-shot route all require the existing protected queue file.

## Watchdog evidence and limits

Fixed authenticated endpoint is loopback 8787 `/scheduler/health` and exact job-filtered `/scheduler/runs`; no redirect, arbitrary URL, method or credential path. Audit credential bytes are never logged. The reader joins fixed root phase/routing/migration records, root routing manifest, authsvc store/incidents, real protected W1/W2 heartbeats and exact launchd generation. State/API hash disagreement is an explicit race refusal, not a reason to waive consistency.

The complete raw semantic document map is verified with duplicate-key rejection. Raw history response and original run event bytes are retained; the only time conversion is exact canonical UTC history `ended_at` to numeric `endedAt`, with the original response bytes retained and deterministic derivation rechecked. Mandatory real `router_admission` evidence proves Scheduler admission and no-effect class; an Agent-written PASS alone is insufficient.

Per document limit is 4 MiB; aggregate capture is capped at 64 MiB with the same duplicate/depth checks. Complete native binary face is already limited to 64 MiB; its typed baseline journal permits up to 384 MiB serialized byte-array representation, avoiding a false 128 MiB ceiling on the observed 43.6 MiB candidate app. Both writes and reads are bounded. These ceilings are no waiver for an oversized actual target.

Current process generation preserves existing NativeService semantics: continuous parent identity and each component's loaded/disabled identity. Periodic PID/run changes do not manufacture a different installed generation; heartbeat freshness and healthy last exit are still mandatory.

All tests are non-root fixtures. Real first-target complete closure, genuine canary and actual signed producer acceptance remain facts the future Owner operation must produce. The parent is freezing actual source/record IDs separately; no fabricated native Goal, runtime or production proof is included here.
