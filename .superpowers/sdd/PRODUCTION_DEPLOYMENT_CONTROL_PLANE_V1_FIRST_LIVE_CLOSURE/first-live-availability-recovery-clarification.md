# Availability recovery without executing the old mutable Node closure

Same accepted Spec and finite dsh first-live package. This is a bounded recovery-plan clarification for independent review before source/package approval; it grants no live effect.

The exact old Node tree contains @rpath/Homebrew loader dependencies. The reviewed future Node closure fixes these paths and is independently validated offline. The existing native maintenance interface correctly refuses the old closure. Constructing a fake old NativeEnrollment or weakening loader validation would add a root execution path outside the trusted closure and is rejected.

The selected failure behavior separates known availability restoration from unknown reconciliation. After a confirmed stop, and only when the complete newly protected app/harness/Node/plist face has already passed exact descriptor/byte/link/metadata/loader validation, the same still-valid Owner operation grant and retained controller/legacy locks may restore the original three-service group's availability using that verified new closure and the original fixed service identities/argv/load flags. It may not execute the old Node closure, undo the retired writer stubs, enable the controller or admit a business deployment. A failed lifecycle/probe/canary remains FAILED even when service availability is restored; record that restoration separately.

If the new closure is incomplete or changed, the grant expired, a concrete effect/recovery intent lacks its result, the service transition is unknown, or another current postimage cannot be proven, stop further effects and preserve exact journals/locks/fences. Do not claim automatic availability recovery. No broad UID kill, repeated start/stop, second request ID, replay or cleanup to regain budget is permitted. An already verified service that was never stopped is not restarted merely to produce a uniform receipt. The still-open enclosing first-live operation is not itself an unknown effect. Recovery eligibility requires a durable explicit observed failed/completed result for every relevant effect, plus the proven current safe face, before publishing a new exclusive one-use recovery intent. A missing concrete effect result must never be relabelled as a known failure to enter recovery. Final closure remains quarantined/FAILED; availability restoration is not a normal deployment rollback success.

Captured old public bytes remain sealed evidence and bounded static repair material. Their existence is not authority to restore old root loader execution. The inode recovery component can restore explicitly known static pre/postimages into fresh inodes, but the driver must not automatically run that general static restoration over a verified new loader face and then claim the services are safe to restart. There is no automatic old legacy entry reactivation. Keys, auth, queue, business/runtime data and historical receipts remain outside restore writes.

Before effects, the exact Owner package must disclose the normal adoption maintenance interruption, the separate later Broker deployment restart, and this conditional recovery limit: a proven new closure can restore service availability while DCP stays disabled/fenced; partial/unknown state may leave affected services stopped pending explicit reconciliation. Nonproduction tests must exercise both branches, prove preserved failure status/no admission, retain original loaded/idle distinctions, and reject stale generation/changed closure/expired grant/recovery replay. This clarification does not represent a promise of automatic recovery from every crash.

The recommendation avoids introducing a second unsafe loader driver solely for rollback. It preserves the accepted fail-closed boundary and makes the practical availability tradeoff explicit in the one complete future Owner authorization request.
