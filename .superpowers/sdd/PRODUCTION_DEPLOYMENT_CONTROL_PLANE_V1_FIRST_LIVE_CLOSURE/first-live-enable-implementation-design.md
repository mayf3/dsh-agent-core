# Fixed first-live and enable join

Same accepted PRODUCTION_DEPLOYMENT_CONTROL_PLANE_V1 authority and explicit parent mandate; nonproduction implementation. Host source freeze remains unchanged. No new role, path API, deployment platform, or root Python launcher.

State graph: CORE_UNKNOWN/FAILED -> refusal; CORE_COMPLETE_CONTROLLER_DISABLED -> exclusive ENABLE_INTENT under the original permanent mutation mutex -> release mutex -> exactly one enable and bootstrap of the fixed controller plist -> daemon READBACK_ONLY -> root authenticates current kernel generation, executable/config/activation/retained listener identity -> exclusive ENABLE_ADMISSION for that generation -> daemon initializes existing standing queue/train and publishes DAEMON_READY -> root authenticates same generation/readiness -> ENABLE_RESULT. Every effect intent without observed result and every timeout is UNKNOWN, with no retry, inverse effect, core replay, or claim of disabled state.

`--first-live-and-enable` is a closed same-binary composition. It invokes core once; the core refuses existing operation intent. After core returns, it reacquires the permanent mutex only to authenticate complete core receipts and exclusively publish enable intent. It releases that guard before launchctl and waiting. A second invoker cannot acquire another enable attempt. Existing --first-live remains core only.

A service startup gate runs before mailbox/queue/producer/recovery/issuer effects. No pending marker preserves existing activation validation. With pending, incomplete/failed/mismatched core or absent exclusive enable intent refuses. The first daemon may acquire its singleton, bind the existing protected listener, and publish fixed protected self-readback, but cannot serve admission or mutate queue. Root publishes admission only after independent readback. The daemon then uses the same listener and existing queue/train initialization and publishes ready. A generation-specific admission cannot authorize a replacement process after an unknown first startup. After durable final enable result, ordinary restarts validate bindings but do not reuse first-lease expiry or require the old PID to remain alive.

All fixed records are descriptor-read strict JSON, protected immutable 0400, no-follow, bounded. Bindings include operation/package/grant/controller, raw complete-core receipt, current configuration and activation digests, and initial exact PID/birth plus socket device/inode. Protected final result is authorization history, not assertion that a past PID is still alive. Root remains responsible for reviewed copy/exec provenance before this command; exec itself adds no trust.

Offline tests: activation with pending but missing/failed/wrong core result refuses; no pending preserves prior gate; exclusive intent rejects second process/replay; admission is initial-generation only until final result; expired first lease refuses initial start but completed restart remains valid; simulated missing effect result remains UNKNOWN; first readback cannot claim normal ready; no effect invocation while mutation guard remains held. Only private fixtures/fake effects, no production socket/root/launchd calls.

## Implementation freeze refinements

Standing controller plist changes exactly three booleans (Disabled=false, RunAtLoad=true, KeepAlive=true), preserving the exact reviewed args, root/wheel, and umask. Old/new byte digests are in the exclusive enable binding; native replacement archives original bytes and rechecks the preimage immediately before rename. The sequence is enable then bootstrap only; RunAtLoad provides the single start, no kickstart.

Initial generation requires genuinely empty protected transactions directory and exactly one completed Applied standing adoption, correct standing receipt, zero executor_pending and quarantine under the permanent mutex. It skips executor recovery for this initial startup only. No issuer serving, ordinary dispatch, poll, or Train tick before final enable-result. Ordinary no-pending/completed starts retain normal recovery and initialize before socket publication; first readback startup alone changes that ordering. Existing daemon-readback consumes the first generation before any replacement socket effect.

CLI: --first-live-and-enable. It checks absent first-live marker/area before invoking core, preserving --first-live as core-only. Success emits FIRST_LIVE_ENABLED with the actual protected enable-result raw hash; unknown enable never emits that success. All source is inert until the separately reviewed host readiness fence is cleared and a new exact Owner-bound package is authorized.
