## Concrete interface and implementation seam to review

New tool/capability: `workflow_current_task_body_complete`, operation `read`.
Eight required arguments bind instance, definition, visit, state, Context,
body kind, body ID and expected SHA. It starts at offset zero without accepting
an old prefix or model-chosen offset, and follows only validated service offsets.
Every page goes through the same caller/target/scope path. Service bodies stay
8,192 bytes or less per page; complete original cap131,072, at most32 pages,
65,536 entity bytes per page, 2MiB accumulated entity bytes, 30s monotonic budget,
1MiB complete JSON result including escaping, and 4KiB closed failure output.
These are proposed fixed product limits, not caller settings.

Two actual source seams need explicit implementation coverage after acceptance:

1. Existing generic transport retries a GET once on401. The new operation must
   opt out through a trusted internal execution control, preserving all old
   defaults and response behavior. It must not accidentally retry a page via a
   second client or a handler restart.
2. Existing successful transport parses the response without this operation's
   wire-byte cap. The new trusted control must bound streamed decoded entity
   bytes before parsing, strictly decode UTF-8, and share the operation's abort
   signal with credential/token/HTTP/read work as applicable. A late credential
   result cannot start a request after the deadline. Generic transport stays
   business-neutral. These controls are not public arguments and are not a new
   credential manager or transport platform.

Success returns the complete string with exact byte count/SHA/binding and page
count. Metadata-only success, a filesystem path, output truncation or a summary
is excluded. Any malformed page/drift/deny/limit/hash error yields one failure
with no partial success. Receipt of verified bytes does not prove comprehension
or a justified verdict. No server-side atomic workflow read-precondition is
claimed or introduced.
