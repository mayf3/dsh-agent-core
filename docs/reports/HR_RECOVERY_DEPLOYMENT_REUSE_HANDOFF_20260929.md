# HR 恢复与部署复用：证据及本地实施交接

日期：2026-09-29。证据基线：`bbffcb0735bf9b1d40e604c8337548afbab10441`。

本文是复盘与有界实施目标，不是新 Product Spec、执行授权或生产操作包。
本 PR 只改文档；没有安装代码、读取受保护状态、重启、重放或清 fence。
源码记录与历史现场不是当前生产事实；接手时通过已有获准入口核对。

## 1. 要解决什么，不重新做什么

目标：在现有部署实现上，让下一次同类发布/维护复用稳定执行机制，
只改变受审制品和已登记参数，而不是再造业务专属安装器、root 例外或查询器。
当前 HR 恢复与后续复用改造分开推进；后者不能成为前者的新前置条件。
原 Deployment Agent 保持生产操作责任；本地实现者只交代码、测试和可部署交接。

不新建 daemon、部署队列、调度平台或通用 root shell；不重启完整 PDC 建设；
不为本交接改共享治理发行物或治理 lock；不把所有服务接入纳入首轮。
本文件的合并不意味着这些部署能力已经实现、获准或上线。

工程判断：这不是“每次发布都必然复杂”，而是普通发布、业务恢复和控制器升级
被串在一起，且实际入口缺口发现得晚。表中证据不能量化耗时，也不能证明全部工作无效。

需要纠正的旧口径：没有观察到 durable intent，不证明进程从未启动，也不授权
换 ID；COMMITTED 回执存在，不证明服务当前健康；root 回执不解决 HR 业务副作用；
安装 reader 是修改，不是只读；“reader 已合并”不能被称为“HR 只剩最后一步”。

## 3. 接手先做一张小表，复用现有记录

在现有 incident/交接记录中填写本次路径所需的能力，不另建平台或强制表单系统：

| 能力 | 已安装入口与版本 | 已有授权范围 | 可复用证据 | 唯一缺口及下一动作 |
|---|---|---|---|---|
| 当前获准的 HR 恢复路径 | 接手时核对 | 不从本文继承 | 引用现有记录 | 不因长期改造而暂停 |
| 普通应用发布/回退 | 接手时核对 | 既有 service profile | 已有有效 proof | 不重复开发已可用部分 |
| 安装与激活分离 | 接手时核对 | 对应已接受模式 | 同真实包形态的测试 | 若缺失，只补最小共享能力 |
| 未完成事务查询/处置 | 接手时核对 | 固定查询与恢复范围 | 断连/取消的测试或回执 | 查询不能先依赖那次修改成功 |
| DS/shim 自身升级与救援 | 接手时核对 | 不冒充 app routine 权限 | 已有安全入口 | 明确与业务发布分开的限制 |

缺口区分为：不会调用、配置缺失、源码未安装、授权不覆盖、真正缺少实现。
这是工作分类，不是新增运行时协议。对每个缺口指定一个负责者和可执行下一步。
既有检查已经覆盖就引用；若受保护证据不可读，准确标明权限缺口，不自行扩大读取。
不要把“有 root 服务”“设计 accepted”或“review PASS”当成可执行权限。

## 4. 两条工作线及退出条件

### A. 当前 HR 恢复：继续原路径，不搭新平台

复用原 Deployment Agent、现有分支/受审候选和原事故记录，不另开相同生产 writer。
分别记录旧 HR turn、shim 初始化事务和 DS 更新事务，保持各自 ID、状态与证据归属。
选定路径要求的查询、旧执行隔离、授权、preimage 和 rollback 条件照常满足。
不能用换 ID、删除历史、清 fence 或一次进程终止来规避未知外部副作用。

恢复验收：所选路径强制条件满足；旧执行与已派发工具的后续副作用被合法隔离；
通过获准入口完成明确的新业务请求并有可追溯读回。旧业务 outcome 可保留 UNKNOWN，
但安装/更新事务若与恢复动作冲突，必须按其契约处置，不因“新请求”而跳过。

### B. 部署复用：只收口实际使用的公共路径

先复用现有获准实现，核对 [PDC V1](../specs/PRODUCTION_DEPLOYMENT_CONTROL_PLANE_V1.md)
及目标服务的当前 authority。以下是实施目标，不能用本文替代缺失的产品或权限决策。
真正缺少受控契约时，只补与该缺口直接相关的决策，不默认新建整个 Spec 体系。

首轮只覆盖同一已有服务的普通版本发布和维护安装/激活。沿用公共锁、制品校验、
依赖保留、回退、journal/receipt；先确认缺口，再补公共能力。不按 HR/P0 名称分叉。
发布请求只引用受保护 catalog 中的 profile 和可信受审制品，不接收任意 root 命令、
脚本、路径或由调用方自选的授权者。哈希证明字节一致，不证明授权。

在需要的最小范围内扩展现有 STATUS/profile 信息，区分 designed/source-ready/
installed-callable/live-verified。实际安装版本与能力从获准读回得出，不靠手填 YES。
未来 profile 激活或执行器改动仍按其受控权限处理，不用 ordinary app 权限自更新。

保留当前必要救援路径；替代路径验证可用、实际使用者迁移后，再退出旧执行路径。
历史审计和回执不删除。控制器升级不得同时破坏唯一救援入口，也不得借此另建平台。

## 5. 用复用与失败场景验收，不用 PR 数量验收

下列都是待执行的验收目标，本文没有声称通过。先在隔离环境覆盖真实生成包、
真实调用链及目标形态元数据；生产验证只由原 Deployment Agent 在相应授权内执行。

| 场景 | 需要的证据 |
|---|---|
| 同一服务 A → B → A | 两个不同受审版本及一次回退，制品/进程/健康证据一致；每次改变制品而非 DS/shim 源码、业务专属安装器或 root 例外。 |
| 维护安装 → 受控激活 | 安装后不普通接单，只有合法激活条件满足才启用；HR 副作用隔离不能仅由通用部署健康检查代替。 |
| 同一请求重复提交、响应丢失 | 查到同一事务；没有第二次安装、重启或业务执行，不能通过新 ID 绕过未完成事务。 |
| 取消、intent 后退出、激活后回执前退出 | 原有查询入口可判定下一步或诚实 UNKNOWN；不先安装 reader 才能证明该安装安全，不把 UNKNOWN 伪装为自动恢复成功。 |
| 目标布局、权限、标识及包大小 | 使用实际生成包和不同角色的标识；错误 host/元数据/包限制在修改前被拒绝，已有服务不受破坏。 |
| 既定维护范围内免密码 | 普通获准调用者在没有临时 sudo ticket 的条件下完成发布、查询和可确定的恢复；权限扩张不能假借旧授权。 |

后续实现交接至少给出：SOURCE_READY、INSTALLED_CALLABLE、BUSINESS_ACCEPTED 的
分别结论、有效证据、未覆盖范围、唯一实际阻点和下一动作。代码完成只代表 source-ready。
真正外部权限缺口只阻塞对应动作，其余安全准备可继续；不许声称已后台自动推进。

`dsh-agent-core` 项目启动，不要求 Owner 为每个新目录重复注册/信任。
